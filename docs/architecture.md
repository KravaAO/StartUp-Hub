# Архітектура Collabix

Collabix — єдиний Django-моноліт. Налаштування проєкту залишаються в `collabix/`; SQLite використовується для локальної розробки.

## Застосунки та відповідальність

| App | Власник | Межі відповідальності та наступні моделі |
| --- | --- | --- |
| `accounts` | Users & Teams | Користувачі, профілі й навички. Наступні: `Profile`, `Skill`, `UserSkill`. |
| `teams` | Users & Teams | Заявки й членство. Наступні: `Application`, `TeamMembership`. |
| `projects` | Projects & Discovery | Проєкти, відкриті позиції й каталог; розвиток `Project` та `ProjectRole`. |
| `workspace` | Workspace | Задачі, дедлайни й дошка. Наступні: `Task`, `TaskComment`. |

Кожен підрозділ відповідає за файли своїх apps: моделі, міграції, admin, майбутні views, тести та локальні `templates/<app>/` і `static/<app>/`. Кореневі `templates/` і `static/` призначені для спільних файлів; Django також знаходить файли в apps. Спільні `collabix/settings.py`, `collabix/urls.py`, майбутній `templates/base.html` і глобальні стилі змінюють лише за погодженням.

## Спільний контракт моделей

- `accounts.User` успадковує `AbstractUser` без додаткових обов'язкових полів. Це єдина модель користувача; `AUTH_USER_MODEL = 'accounts.User'`.
- `projects.Project`: `owner` (User), `title`, `short_description`, `description`, `status` (`draft`, `recruiting`, `active`, `archived`), необов'язковий `deadline`, резервний `budget` (Decimal, за замовчуванням 0), `is_public`, `created_at`. Початковий статус — `draft`, проєкт за замовчуванням непублічний. `budget` не використовується у фінансовій логіці й прихований в admin.
- `projects.ProjectRole`: `project` (Project), `title`, `description`, `is_open`, `slots`. За замовчуванням позиція відкрита й має одне місце.

Моделі учнів поки не створені. Рекомендовані зв'язки для узгодження перед реалізацією: `Profile` → User; `UserSkill` → User і `Skill`; `Application` → User, Project та, за потреби, ProjectRole; `TeamMembership` → User і Project; `Task` → Project та User; `TaskComment` → Task і User. Точні ролі користувачів, обов'язковість та поведінку видалення визначають власники моделей разом із командою.

## Залежності та міграції

Напрямок залежностей: `accounts` не імпортує бізнес-моделі інших apps; `projects` використовує User; `teams` може використовувати User, Project і ProjectRole; `workspace` може використовувати User і Project. Не дублюйте сутності та не створюйте циклічних залежностей міграцій. Для зв'язків з користувачем використовуйте `settings.AUTH_USER_MODEL`, для зв'язків з іншими apps можна використовувати рядки на кшталт `'projects.Project'`.

Міграція `accounts/0001_initial.py` створює користувача, а `projects/0001_initial.py` залежить від налаштованої моделі користувача. На новій базі застосовуйте всі міграції командою `python manage.py migrate`. Якщо локальна база вже має міграції стандартного `auth.User`, заміна моделі користувача після їх застосування складна: не видаляйте дані автоматично, узгодьте окрему міграцію даних або створення чистої навчальної бази.

Кожен app має власну послідовність міграцій. Якщо кілька учнів одночасно змінюють моделі одного app, узгодьте зміни до створення міграцій; не редагуйте вже інтегровані міграції без спільного рішення. Після оновлення від `develop` перевіряйте порядок і конфлікти міграцій, `makemigrations --check --dry-run` та `migrate` на чистій базі.

## Робочий процес

1. Кожен учень створює власну `feature/...` гілку від актуальної `develop` і змінює насамперед файли свого app.
2. Зміни спільних контрактів та файлів узгоджуються з їхніми власниками й усіма залежними підрозділами.
3. Інтегруйте невеликими Pull Requests: перед інтеграцією оновіть гілку від `develop`, перевірте міграції та отримайте code review.

## Локальні налаштування

Встановіть залежності з `requirements.txt`, виконайте `python manage.py migrate`, а для доступу до `/admin/` — `python manage.py createsuperuser`. Значення в `.env.example` треба експортувати в середовище вручну: автоматичне завантаження `.env` не налаштоване. Для локальної розробки без ключа використовується явно небезпечний резервний ключ. Для production встановіть `DJANGO_DEBUG=0` і довгий випадковий `DJANGO_SECRET_KEY`; без ключа запуск завершиться помилкою. Інші production-налаштування, зокрема `ALLOWED_HOSTS`, слід налаштувати перед розгортанням.
